# 反思输入契约显式化计划

## 1. 背景

### 1.1 故障现象

天使之魂（angel_memory）与天使之心 2.x 搭配时：

- 群聊日志恒为 `[反思调度] 使用天使之心聊天记录: processed=0 + latest_unprocessed_user=0`
- 紧接着 `[反思调度] 本轮无消息入池`，反思永不触发
- 记忆库为空，召回恒为 0（`链式回忆: 实体记忆=0, 类型记忆=0, 总计=0`）
- 灵魂能量恒为 `E=0.0`，不共鸣
- 用户画像通道同样空转

### 1.2 直接原因

angel_memory 用 `is_processed` 字段判断"本轮新增"：

```python
# core/deepmind.py:841
processed = [msg for msg in chat_records if msg.get("is_processed", False)]
# core/deepmind.py:848
and msg.get("is_processed", True) is False
```

angel_heart 已在 `317c520`（2026-07-13，2.0.0）退役该字段，写入时主动清理：

```python
# astrbot_plugin_angel_heart/core/conversation_ledger.py:365
message.pop("is_processed", None)
```

字段缺失后两个判断恒不成立，合并结果恒为空列表。

### 1.3 根因（比 1.2 更深一层）

`is_processed` 只是表象。真正的问题是**跨插件契约依赖了对端内部字段，且该字段承载了错误的语义**：

| 问题 | 说明 |
| --- | --- |
| 语义错位 | `chat_records` 是"当前连续块的全量快照"，不是增量。用快照模拟增量，必须靠切分，而切分依赖 role 结构 |
| 切分不可靠 | 压缩会把旧 assistant 折叠进摘要（`_build_rule_summary`），边界消失 |
| 生产方不知情 | angel_heart 无法知道自己的压缩策略变化会打断 angel_memory 的反思 |
| 消费方无权控制 | angel_memory 无法约束别人的字段 |

**关键认知**：反思真正需要的"本轮新增"根本不必从 `chat_records` 里推断——

- 本轮用户消息 → `event` 自身
- 本轮助理回复 → `response.completion_text`（本次调用产出）

把"增量"寄托在别人维护的账本字段上，才是根因。这已是本仓库第三次因该字段出问题（`184865a` 引入，字段退役后失效）。

### 1.4 连带发现的独立缺陷

| # | 缺陷 | 位置 | 影响 |
| --- | --- | --- | --- |
| D1 | `latest_assistant_text` 从 `chat_records` 倒查最后一条 assistant | `core/deepmind.py:911-921` | 快照生成于主模型回复**之前**，取到的是**上一轮**旧回复；反思提示词「你的最新回复」内容错误 |
| D2 | 反思缓冲 `_reflection_states` 纯内存 | `core/deepmind.py:163` | 攒到 5 轮时重启，5 轮缓冲丢失；阈值 6 轮 / 600 秒，丢失窗口不小。**评审后决定不修**，理由见 4.5 |
| D3 | `create` 动作不按 judgment 去重 | `llm_memory/components/memory_sql_manager.py:1983` | 一旦重复反思，直接产生重复记忆条目 |

## 2. 目标

- 消除跨插件隐式契约：由 angel_heart **显式声明**快照结构，angel_memory **只读显式字段**
- 反思输入与生产方压缩策略解耦：压缩怎么改，都不影响消费方
- 修掉 D1、D3（D2 评审后放弃，见 4.5）
- 双向兼容：任一插件单独升级都不报错

## 3. 非目标

- 不改检索/重排/向量索引逻辑
- 不改反思提示词正文（仅修正填入的数据）
- 不碰 `small_model_prompt_builder.format_note_query`：全仓库无调用点，属死代码，改它无意义
- 不做 `main.py` 工具 `plugin_context` 兜底、不做 `on_llm_response` 最小上下文构造：与本次故障无关，不扩大改动面

## 4. 方案：契约显式化

### 4.1 数据所有权

| 数据 | 权威来源 | 理由 |
| --- | --- | --- |
| 本轮用户消息 | `event` | 事件本身即代表这一轮 |
| 本轮助理回复 | `response.completion_text` | 回复是本次调用产出，不该去历史里翻 |
| 对话背景 | `chat_records[:historical_count]` | 摘要/历史前缀，只作背景 |
| 当前连续块 | `chat_records[historical_count:]` | 供画像、query 使用的"当前批次" |

### 4.2 angel_heart 侧：新增显式边界字段

`core/utils/context_utils.py` 的 `json_serialize_context` 增加一个可选参数：

```python
def json_serialize_context(
    chat_records: List[Dict],
    decision: Union["SecretaryDecision", Dict],
    historical_count: int = 0,
) -> str:
```

输出结构增加：

```json
{
  "chat_records": [...],
  "historical_count": 1,
  "secretary_decision": {...}
}
```

`historical_count` 语义：**`chat_records` 前 N 条属于历史前缀（摘要/压缩块），其后为当前连续块。**

调用点 `roles/front_desk.py:997` 的 `full_snapshot = historical_context + recent_dialogue`，直接传 `len(historical_context)`。

同时把该值同时写入日志，便于排障：

```
AngelHeart[chat]: 上下文已注入 event.angelheart_context
  records=N historical=1 batch=M
```

### 4.3 angel_memory 侧：改为读显式字段

新增私有方法 `_split_chat_snapshot`：

```python
def _split_chat_snapshot(
    self, chat_records: List[Dict], historical_count: int
) -> tuple[list, list]:
    """按生产方声明的边界切开快照：返回 (背景, 当前批次)。"""
```

分支规则：

| 输入 | 处理 |
| --- | --- |
| 有 `historical_count`（新契约） | 直接按声明切分 |
| 无 `historical_count`、有 `is_processed`（旧契约） | 沿用旧逻辑，行为不变 |
| 只有 `chat_records`（当前 2.x，无任何标记） | 兜底：从最后一条 `role=assistant` 之后切分 |

三处消费点统一改造：

1. `organize_and_inject_memories`（`core/deepmind.py:346`）—— `unprocessed_chat_records` 改为"当前批次"
2. `_build_reflection_records_for_turn`（`core/deepmind.py:831`）—— 入池记录改为"当前批次"
3. `_build_reflection_input`（`core/deepmind.py:911`）—— `latest_assistant_text` 改用 `response.completion_text`

### 4.4 D1：助理回复改取 response

```python
def _build_reflection_input(self, event, response, session_id):
    response_text = (
        getattr(response, "completion_text", str(response))
        if response is not None else ""
    )
    ...
    # 倒查逻辑仅作为 response 缺失时的兜底
    latest_assistant_text = str(response_text).strip() or fallback_from_records
```

### 4.5 D2：反思缓冲（已放弃）

**结论：不做持久化，维持纯内存态。**

原计划新增 `reflection_buffer` 表承载未消费的反思轮次，评审后放弃。理由：

- 缓冲存活窗口本就短暂（凑满 6 轮或 10 分钟即消费），稳定部署下重启少，丢失量有上限
- 新增表意味着多一个数据源、一份可能与内存失同步的副本、每轮一次写盘
- 收益只覆盖"恰好在攒够前重启"的边界场景，不值得承担长期维护成本

随之取消的相关改动：
- `memory_sql_manager` 的 `reflection_buffer` 表与三个读写方法
- `DeepMind` 的 `_persist_reflection_state` / `_restore_reflection_state` / `_sync_reflection_state`
- 对应的 4 条持久化测试

保留的行为不变：`_reflection_states` 仍为纯内存，进程重启即清空，与改动前一致。

### 4.6 D3：create 动作去重

`process_feedback` 的 `create` 分支，在 `remember()` 前按 `(judgment, memory_scope)` 查重；命中则跳过并计入日志计数，不新增条目。

判断口径放在 SQL 层（`memory_records` 已有 `idx_memory_judgment` 索引），不做模糊匹配，只做规范化后精确比对。

## 5. 兼容性

| 组合 | 行为 |
| --- | --- |
| 新 heart + 新 memory | 走 `historical_count`，精确切分 |
| 旧 heart + 新 memory | 无 `historical_count`，按角色兜底切分（等价旧行为或更优） |
| 新 heart + 旧 memory | `historical_count` 被忽略，旧 memory 行为不变（仍然坏，但不报错） |

关键性质：**两侧均为可选字段，任一单独升级都不会抛异常。**

## 6. 测试

### 6.1 angel_heart

- `json_serialize_context` 有 `historical_context` 时输出正确的 `historical_count`
- 无 `historical_context`（纯 recent）时 `historical_count=0`
- 缺省调用不传该参数时输出 `historical_count=0`（向后兼容）

### 6.2 angel_memory

沿用 `tests/test_reflection_message_identity.py` 的 stub 风格新增：

1. **回归（当前必红）**：喂无 `is_processed` 的 2.x 快照 → 断言产出记录数 > 0
2. 有 `historical_count=1` 的快照 → 断言批次不含摘要，且不含上轮 assistant
3. 旧快照（带 `is_processed`）→ 断言行为与改前一致
4. `latest_assistant_text` 取自 `response`，而非快照里的旧 assistant
5. create 去重：同 judgment 提交两次 → 断言只成功创建一次

### 6.3 执行方式

插件运行在 Docker 容器内，必须在容器内跑：

```bash
docker exec astrbot bash -lc 'cd /AstrBot/data/plugins/astrbot_plugin_angel_memory && python -m pytest -q'
docker exec astrbot bash -lc 'cd /AstrBot/data/plugins/astrbot_plugin_angel_heart && python -m pytest -q'
```

## 9. 风险与回退

| 风险 | 缓解 |
| --- | --- |
| `historical_count` 与 `chat_records` 长度不一致 | 消费方做边界钳制（`min/max`），越界时退化为角色兜底并打 WARNING |
| 压缩后 `historical_context` 含多条 | `historical_count` 是计数而非固定值，天然支持多条 |
| 持久化表写入失败 | 降级内存 + INFO 日志，不阻断反思主流程 |
| 去重误杀不同记忆 | 仅精确匹配规范化 judgment + 同 scope，不做相似度 |

回退：两侧改动均为独立提交，`git revert` 单个提交即可。数据库新增表为 `CREATE TABLE IF NOT EXISTS`，回退不破坏数据。

## 10. 验收标准

1. 群聊触发反思后，日志出现 `[反思调度] 入缓冲 records>0`，且 `pending_turns` 正常累积
2. 攒满 6 轮后出现 `[反思调度] 触发` 与 `[反思执行] 完成 ... new>0`
3. 记忆库出现新条目，召回不再恒为 0
4. 反思提示词中「你的最新回复」等于本轮实际回复
5. 连续两轮反思之间，不出现同一段对话被重复归纳为多条记忆
6. ~~重启后未消费的缓冲不丢失~~（D2 已放弃，不再要求）
